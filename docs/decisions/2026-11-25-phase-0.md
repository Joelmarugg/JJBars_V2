# Entscheidungen Phase 0 (25. Nov. 2026)

Quelle: Plan "JJBars 2 – Plan für den sauberen Neuaufbau" und `docs/PARITY.md`.

## Grundentscheidungen

1. **Neuaufbau:** frisches Projekt in einem neuen Repository (`JJBars_V2`). Das alte Repository `JJBARS_2` bleibt mit dem Tag `v1-legacy` als Referenz.
2. **Identität:** anonym starten (Firebase Anonymous Auth mit Persistenz über AsyncStorage; nach einem App-Neustart muss dieselbe UID erscheinen, per Test geprüft). Ein Login lässt sich später nachrüsten, indem das anonyme Konto verknüpft wird.
3. **Signatur:** der bisherige Schlüssel, also der `debug.keystore` aus dem alten Repository (Alias `androiddebugkey`). Das ist eine Annahme des Besitzers und wird im Datenerhalt-Test bestätigt. Ein Update setzt dieselbe Paketkennung `com.jjbars.app` und denselben Schlüssel voraus.
4. **Firebase:** Realtime Database mit JS-SDK, kein App Check.
5. **Navigation:** Expo Router mit typisierten Routen.
6. **Plattformen:** nur Android im Neuaufbau; iOS optional in Phase 8.

## Technik

- **Expo SDK 58** (React Native 0.88). Rückfall auf SDK 57 nur, wenn in Phase 1 der erste Development-Build oder das erste `preview`-APK scheitert. Node 22.13 oder neuer.
- Development Builds statt Expo Go. TypeScript im strikten Modus.

## Sicherheit und Daten

- Die Firebase-Regeln sind heute offen (Lesen und Schreiben). Das bleibt bewusst bis zur Auslieferung der neuen App (Phase 7); vorher gibt es einen JSON-Export der Datenbank als Backup (am 25. Nov. 2026 gemacht).
- Der alte API-Key wird erst mit der Auslieferung der neuen App rotiert (Phase 7). Im neuen Repository taucht er nicht auf.
- Gemeinsames Bearbeiten (F8): Geteilte Workouts darf jeder überschreiben, nach Rückfrage. Die Regeln akzeptieren nur gültig aufgebaute Workouts mit begrenzter Größe; löschen darf nur der Ersteller (`ownerUid`).
- Katalog (F15): Die aktuelle Datenbank steckt als Sicherung in der App. Updates kommen über ein Manifest (Version, URL, Prüfsumme); die neue Datei wird erst heruntergeladen und geprüft, dann ausgetauscht.
